# the-tree-says-what-it-runs

The tree is carrying the forge's upgrade and the operator's own fix, uncommitted.

Observed, opening this project the day after the forge's upgrade: the project's own
copies of the shared runtime arrived refreshed but uncommitted - its scripts, its role
prompt and engineering article, and two feature files still stamped from the night
before - and sitting in the same pile is the operator's one-word correction to this
project's configuration, the typo (`window-inviisble`) that stopped the project starting
at all. A macOS `.DS_Store` was among the untracked noise as well; the forge's ignored
lines carry that now, so it is not to be committed as content.

What the operator wants: the project's history says what the project runs. Their words,
when the local edits came up - "About those local edits I think they can just be
committed no?" - and, when I offered to have that be a card of its own, "ok I guess we
can make it a card". So commit the composition refresh, and the operator's configuration
fix with it: the fix is what makes this project startable again, so it must not be left
behind, dropped, or committed anywhere but with the tree it belongs to.

What this is not: the refresh is not to be re-run, revised, or trimmed to make the
commit smaller. The project's copies of the runtime are whatever the composition wrote
them as, and the whole point is that the tree and its history agree - so the work is the
commit, not a judgement about what should have changed. Leave nothing from the refresh
uncommitted when the card is done.
